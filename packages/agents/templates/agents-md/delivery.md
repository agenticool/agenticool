## Autonomous delivery

- Authority: a delivery request authorizes issue claims, project moves, commits, pushes, ready-for-review PRs, stack links, and retargeting the base of the delivery owner's own stacked PRs after a merge, as the sync in [stack operations](.agents/skills/{{prefix}}stack/SKILL.md) does. Filing authorizes issue publication. A manual review of a pull request authorizes one posted review on that PR and nothing else: no edits, no approval, and a change request only for a `REQUEST CHANGES` verdict from a GitHub account other than the PR author. Automatic pre-PR reviews and branch reviews write nothing to GitHub. Merges, deployments,{{#infrastructure}} infrastructure applies,{{/infrastructure}} destructive operations, and changes to GitHub repository settings, CI secrets, or agent tool settings require explicit user authorization.
- Before creating or using a worktree, read and follow [Agent worktree isolation](.agents/worktree-isolation.md).
- When a leaf lacks Priority or Size, set Priority to P2 and Size from the scope, as `{{docs.triage}}` defines. Missing tracker metadata alone does not block delivery.
- [Leaf delivery](.agents/skills/{{prefix}}implement/references/delivery.md) owns the delivery gate, stacking on unmerged prerequisites, review thresholds, exact-SHA approval, reviewer packets, PRs, and handoff results. A review handoff after the final push sends the review packet that leaf delivery defines, taking the base SHA from `git merge-base <base> HEAD`, and a rework handoff adds the existing PR URL. Reviewers follow [Independent code review](.agents/review.md) and stay read-only. Load those procedures for delivery or review rather than copying them into assignments.
- Make your own GitHub calls through REST with `gh api`: issues, PRs, comments, labels, assignees, sub-issues (`repos/<repo>/issues/<n>/sub_issues` and `/parent`), issue dependencies (`/dependencies/blocked_by` and `/dependencies/blocking`), and Projects v2 (`users/<owner>/projectsV2/<n>` or `orgs/<owner>/projectsV2/<n>`, with `/fields` and `/items`). `gh issue`, `gh pr`, `gh project`, and `gh api graphql` use GraphQL, whose hourly limit agents share with Actions tokens. Use GraphQL only when REST lacks the operation, such as reading a PR's closing issues, and switch to REST when it is rate-limited. The tracker workflows and `npx agenticool-tracker` keep their GraphQL calls, even when you run them.
